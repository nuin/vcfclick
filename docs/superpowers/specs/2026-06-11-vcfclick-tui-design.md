# vcfclick TUI Design

## Summary

Add an optional Textual-based terminal UI exposed as `vcfclick tui`. The TUI
starts from genomics workflows, not generic SQL: the home view is a
gene/region summary screen. Operations and SQL remain adjacent modes so users
can manage local databases and inspect or edit the SQL behind every result.

The first release keeps implementation inside the existing package and reuses
the current `storage`, `annotations`, and CLI helper layers. It does not try to
be a Harlequin plugin in v1.

## Goals

- Provide a Harlequin-like terminal workspace for `vcfclick` without making SQL
  the first screen.
- Make gene and region exploration the default path.
- Keep generated SQL visible and editable.
- Surface database operations needed during ordinary exploration.
- Keep the existing CLI lightweight by making Textual an optional dependency.
- Keep query, parsing, and summary behavior testable outside Textual widgets.

## Non-Goals

- Full Harlequin compatibility or plugin integration.
- Natural-language query generation inside the TUI.
- Multi-query notebook behavior.
- Rich asynchronous ingest progress dashboards.
- Editing stored variant, genotype, sample, or ingestion rows.

## User Model

The primary user is a bioinformatician or genomics researcher working with one
local `vcfclick` database at a time. They may know SQL, but their first question
is usually genomic: a gene, a coordinate range, a cohort, or a variant. The TUI
should make the database inspectable without hiding the SQL that ran.

## Command Surface

Add:

```bash
vcfclick tui [--db NAME]
```

If `--db` is provided, the TUI starts with that database active. If omitted, the
app starts with no active database when none can be inferred, and the user picks
from the database list. The command should fail gracefully when Textual is not
installed, with a message that explains how to install the TUI extra.

## Architecture

Add a `tui/` package:

- `tui/app.py`: Textual app shell, global navigation, active database state.
- `tui/screens/locus.py`: gene/range input, summary panels, variant preview.
- `tui/screens/operations.py`: database list, active database switching,
  database info, stats, paths, and basic ingest launcher.
- `tui/screens/sql.py`: SQL editor, result table, generated SQL handoff, and
  query history for the current session.
- `tui/services.py`: small adapter layer over existing Python APIs in
  `storage`, `annotations`, and CLI helper modules.

The TUI should call Python services directly instead of shelling out to
`vcfclick db ...`. This keeps error handling structured, avoids parsing CLI
text, and makes the non-UI behavior testable with normal pytest tests.

## Navigation Model

The app has three modes:

- **Locus**: default home view. Enter a gene symbol or coordinate range. The
  v1 implementation must support gene symbols and `chrom:start-end` ranges.
  Known variant lookup can be added after v1.
- **Operations**: database list, active database selection, info, path, stats,
  and basic ingest entry points.
- **SQL**: editor and result table. This can be opened empty or prefilled with
  SQL generated by the locus summary or drilldown actions.

The visual priority is Locus first, Operations second, SQL third. SQL should be
one action away from every generated result, not hidden in logs or debug output.

## Locus Flow

1. User selects or confirms the active database.
2. User enters a gene symbol such as `BRCA1` or a range such as
   `chr17:43044295-43125483`.
3. The service layer resolves the input:
   - gene symbols use `annotations.position_for_gene`;
   - coordinate ranges are parsed locally;
   - invalid or ambiguous inputs produce recoverable UI errors.
4. The service layer runs summary queries against the active database.
5. The Locus screen renders summary panels and a small variant preview.
6. Every panel exposes the SQL that produced it and can send that SQL to the SQL
   mode for editing and rerun.

## Locus Summary Panels

The first result screen emphasizes summary before tables:

- resolved locus: symbol, chromosome, start, end, genome convention;
- row counts in the locus: variants, non-reference genotype rows, samples where
  relevant;
- cohort/sample coverage where the `samples` table has cohort data;
- allele-frequency or carrier-count summary by cohort when enough data exists;
- annotation state: whether gene annotations are loaded and whether ClinVar
  lookup can be used for variant drilldowns;
- quality-field population hints for `gq` and `dp`, so users can see when
  default quality filters would silently drop genotype-only public datasets;
- overflow key hints from `info_extra` and `format_extra` when backend support
  exists;
- variant preview table with filters and an open-in-SQL action.

The app should avoid rendering a full wide variant table before the summary has
shown whether the locus contains useful data.

## Operations Mode

Operations mode covers the parts of `vcfclick db ...` users need while
exploring:

- list local databases;
- switch active database;
- show database path;
- show basic info counts;
- run stats where the active backend supports it;
- provide an ingest entry point for existing files.

In v1, ingest can be modest: a form that starts an ingest using existing ingest
APIs is enough. A full progress dashboard is deferred.

Backend limitations must be explicit. For example, current stats behavior is
chDB-specific; the TUI should render a clear unsupported-feature panel on
DuckDB instead of failing.

## SQL Mode

SQL mode provides:

- multiline SQL editor;
- run action against the active database;
- result table;
- error panel for SQL exceptions;
- current-session query history;
- ability to receive generated SQL from Locus or Operations actions.

The SQL mode should use the same active database state as Locus and Operations.
Result rendering can start simple: table output with bounded row display is
acceptable for v1.

## Service Layer

The service layer should expose small functions or classes for:

- database listing and metadata;
- active database validation;
- locus input parsing;
- gene resolution;
- summary SQL generation;
- summary query execution;
- variant preview query execution;
- SQL execution for user-entered queries.

Service return values should be structured Python data, not formatted terminal
strings. Include the SQL string with every query result that came from a
generated query.

## Error Handling

The TUI should show recoverable error panels for:

- no active database;
- selected database does not exist;
- invalid coordinate range;
- gene not found;
- annotation store not loaded;
- empty locus result;
- backend unsupported feature;
- SQL syntax or execution error;
- ingest validation or runtime error.

Errors should not crash the app unless they indicate a programmer error outside
normal user input.

## Packaging

Textual should be optional. The base CLI install should not pull in TUI
dependencies unless the user asks for them. The package metadata should expose a
TUI extra or dependency group suitable for:

```bash
pip install "vcfclick[tui]"
```

or the equivalent `uv` command.

## Testing

Use normal pytest tests for the service layer:

- coordinate parser accepts valid ranges and rejects invalid ranges;
- gene resolution handles found and not-found cases;
- generated SQL includes the resolved locus and active database assumptions;
- summary functions return structured data and SQL;
- backend unsupported features return typed errors rather than raw exceptions.

Keep Textual tests focused:

- app starts;
- database picker renders;
- locus search delegates to the service layer;
- generated SQL can be handed to SQL mode;
- SQL errors render without crashing.

## First Implementation Slice

The first implementation slice should ship a useful read-only explorer before
the full v1 operations surface is complete:

1. Optional TUI dependency and `vcfclick tui` command.
2. App shell with active DB state and three modes.
3. Locus input supporting gene symbols and `chrom:start-end`.
4. Summary queries and generated SQL display.
5. Variant preview table.
6. SQL mode handoff and rerun.
7. Operations mode database list/info/path.

Stats and ingest can follow once the core locus-to-summary-to-SQL loop is
working.

## V1 Completion Criteria

V1 is complete when the first implementation slice is extended with:

- Operations stats action with explicit unsupported-backend handling.
- Basic ingest launcher that uses existing ingest APIs.
- Recoverable UI errors for every case listed in the error handling section.
- Service-layer pytest coverage for parsing, summary query generation, backend
  unsupported features, and SQL execution errors.
- Textual smoke tests for app startup, DB selection, locus search, and SQL
  handoff.
